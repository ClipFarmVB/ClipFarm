# OCR (jersey numbers) — deliberately NOT installed. `ml/pipeline/ocr.py` has
# no call sites; CF-7 (#31) is its intended consumer and is unscheduled. Two
# reasons this file does not carry the pins in the meantime: they are several
# hundred MB in every dev install, and `paddleocr==2.9.1` requires `numpy<2.0`.
# Among the constraints this file's dependencies declare in their own metadata,
# that is the only one holding numpy below 2 unconditionally. `ultralytics`
# also caps numpy below 2, but only on darwin (`numpy<2.0.0; sys_platform ==
# "darwin"`), so a macOS install stays capped until ultralytics is bumped too —
# and the bump is not free: the marker survives through 8.3.69 and is gone in
# 8.3.70, which replaces it with an unconditional `numpy<=2.1.1`. 8.3.253
# carries no unconditional cap at all, so the version chosen matters.
#
# `inference-sdk>=0.9.0` below is worth CF-363's attention for the opposite
# reason. It is unpinned, and its releases from 0.50 on require `numpy>=2.0.0`,
# so today it resolves to 1.5.1 alone but is silently walked back to 0.45.1
# whenever `numpy==1.26.4` is in the same install. The numpy-2 move frees it;
# until then this file quietly installs a much older SDK than it looks like.
#
# It is NOT the only thing holding the repo on numpy 1, and CF-363 should not
# read it that way: this file's own `numpy==1.26.4` is a harder ceiling still,
# and it is repeated in Dockerfile.api, ml/modal_pose.py, api/requirements-dev.txt
# and .github/workflows/ci.yml. A pin-consistency test requires the first three
# to agree, so those move in lockstep or not at all. Dropping these two pins
# removes one obstacle in front of that work; it does not clear the way.
#
# `read_jersey_numbers` imports PaddleOCR lazily and returns all-`None` with a
# warning when it is absent, so the module stays importable without them.
#
# CF-7 inherits a PORT, not a working module. `ocr.py` targets paddleocr 2.x
# and does not run on 3.x, which is the release that drops the numpy ceiling.
# Three breakages, in call order — anchored on the code rather than on line
# numbers this file has no way to keep correct:
#   PaddleOCR(show_log=False) — 3.x has no `show_log` and does not map it, so
#     `parse_common_args` raises ValueError. The lazy import guard only catches
#     ImportError, so this is a hard failure, not the graceful all-`None` path.
#   ocr.ocr(torso, cls=False) — 3.x forwards `ocr()` to `predict()`, which
#     takes no `cls`. TypeError.
#   text, conf = item[1] — 3.x returns PaddleX `OCRResult` objects, not the
#     2.x nested-list shape this unpacks.
# The last two are unlike the first in the way that matters here: both run
# inside the per-box `try` whose `except Exception` logs and appends `None`.
# Fixing only the constructor therefore buys a full run of `None`s and one
# traceback per box — the silent no-op, not a stop.
#
# So do not re-add a pin here expecting the module to work. Port `ocr.py` to
# 3.x as part of CF-7, then add BOTH `paddleocr>=3` and a `paddlepaddle` pin.
# The framework is not pulled in for you: paddleocr 3.7.0 requires
# `paddlex[ocr-core]` and never names paddlepaddle, and neither does paddlex —
# which is why this file carried it on its own line. Its absence surfaces from
# paddlex rather than as the ImportError `ocr.py` guards, so that path does not
# degrade to all-`None` either. Pinning `paddleocr==2.x` instead would work
# today and put the numpy ceiling straight back.

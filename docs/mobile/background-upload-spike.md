## 1. What the app actually has to talk to

The native uploader is a client of an upload path that already exists and is
not changing shape for this epic. Getting the constraints right matters more
than the platform trivia, because two of the three hard problems below are
ours, not Apple's or Google's.

### 1.1 The protocol, from the code

`[repo]` — `api/app/routers/games.py`, `api/app/services/storage.py`,
`api/app/config.py`, `web/src/lib/upload.ts`.

```
POST /games/uploads              → UploadTicket  (all presigned URLs, up front)
   PUT each part directly to R2  (never touches our api)
POST /games/{id}/uploads/complete  {parts: [{part_number, etag}, …]}
```

Three settings shape everything (`api/app/config.py`) `[repo]`:

| setting | value | what it does |
|---|---|---|
| `single_put_max_bytes` | 100 MiB | at or below this, one PUT; above it, multipart |
| `upload_part_size_bytes` | 100 MiB | multipart slice size, sliced client-side |
| `upload_url_ttl_seconds` | 43 200 (12 h) | **one expiry shared by every URL in the ticket, with no renewal path** |
| `max_upload_bytes` | 8 GiB | the cap `[repo]`, and the size that sets the worst case below |
| `abandoned_upload_hours` | 24 | sweep window for tickets that never completed |

The client and server agree on part boundaries without exchanging them: both do
the same ceiling division (`storage.plan_part_count` and `upload.ts::planParts`)
`[repo]`. A native module must use the same arithmetic or the assembled object
is wrong.

Two details that a native implementer will otherwise get wrong:

- **Part URLs sign only `host`.** A part URL generated by our code carries
  `X-Amz-SignedHeaders=host` `[measured-here]`, so any extra request header
  (including a `Content-Type` the platform adds for you) is unsigned and
  harmless. `web/src/lib/upload.ts` deliberately sets no `Content-Type` on
  parts `[repo]`; a native module does not have to replicate that caution, but
  it must not *contradict* the single-PUT URL, where `ContentType` **is**
  signed (`storage.presign_put`) `[repo]`.
- **The ETag CORS trap does not apply.** `upload.ts` has a whole failure mode
  around `ExposeHeaders: ETag` `[repo]`. Native HTTP has no CORS, so the ETag is
  always readable. One less thing for CF-323/CF-324.

### 1.2 How many parts, and how big the ticket gets

Signed with boto3 through the same `generate_presigned_url("upload_part", …)`
call `storage.presign_upload_part` makes, against an R2-shaped endpoint with
realistic-length dummy credentials. Part counts are `[arithmetic]` (ceiling
division); URL and ticket sizes are `[measured-here]`.

R2 upload-id length varies, and it lands inside every URL, so the ticket size is
given for a 96-character upload id; ±32 characters of upload id moves the ticket
size by about ±6 %.

| file | part size | parts | signed part URL | full ticket JSON |
|---|---|---:|---:|---:|
| 2 GB | 100 MiB | 21 | ~513 chars | 11.4 KiB |
| 2 GB | 64 MiB | 32 | ~513 chars | 17.2 KiB |
| 2 GB | 32 MiB | 64 | ~513 chars | 34.1 KiB |
| 2 GB | 16 MiB | 128 | ~513 chars | 68.1 KiB |
| **8 GB** (the cap) | **100 MiB** | **82** | ~513 chars | **43.7 KiB** |
| 8 GB | 64 MiB | 128 | ~513 chars | 68.1 KiB |
| **8 GB** | **32 MiB** | **256** | ~513 chars | **136.1 KiB** |
| 8 GB | 16 MiB | 512 | ~513 chars | 272.1 KiB |

The ticket's own guess of "~256 presigned URLs" for 8 GB at 32 MiB is exactly
right, and 100 MiB gives 82 parts, not 80.

**The ticket size is a non-issue.** 136 KiB of JSON over HTTPS on a phone is one
or two round trips. The 10 000-part S3/R2 ceiling is nowhere in reach — even
16 MiB parts on a cap-sized file is 512.

**The signing cost is also a non-issue**, which is worth stating because
`create_upload` presigns every part in a synchronous list comprehension on the
event loop `[repo]`:

| parts | wall time to sign |
|---:|---:|
| 82 | 24 ms |
| 128 | 34 ms |
| 256 | 65 ms |
| 512 | 155 ms |

`[measured-here]`, in the container, on one core. Presigning is local HMAC with
no network, so this is CPU only. At 256 parts it is 65 ms of event loop, which
is noticeable but not a problem; at 512 it is 155 ms and worth moving to
`run_in_threadpool` if we ever go that small. It is **not** a reason to prefer
larger parts.

### 1.3 The three things that will actually bite

These are ours. They are not documented anywhere else, and CF-323/CF-324 will
hit all three.

**(a) There is no way to re-issue a ticket.** The only routes are
`GET /games/upload-config`, `POST /games/uploads`, and
`POST /games/{id}/uploads/complete` `[repo]`. There is no endpoint that
re-presigns parts for an *existing* `upload_id`, and `storage.py` has no
`list_parts` wrapper `[repo]`. So today, if the 12 h TTL lapses mid-transfer,
every remaining part URL 403s, and `upload.ts` correctly treats a 403 as
non-retryable `[repo]`. The already-uploaded parts are still sitting in R2 under
the `upload_id`, and there is no way to reach them. **The user re-uploads from
zero.**

This is the single most important finding for the native modules, and it is an
api gap, not a platform one. A backgrounded upload is exactly the case where a
multi-hour stall is normal — see §3 on iOS discretionary scheduling.

**(b) A user's next presign can delete their own in-flight upload.**
`_sweep_abandoned_uploads` runs on every `POST /games/uploads`, finds that
user's rows in status `uploading` older than `abandoned_upload_hours` (24 h),
aborts the multipart upload and deletes the object `[repo]`. It does not and
cannot know that one of those rows is a live background transfer. A filmer who
starts game 1 in the evening, whose phone defers it overnight, and who starts
game 2 the next evening, destroys game 1.

In practice (a) fires first — 12 h < 24 h — so today this is the second
tripwire, not the first. Both need a Lane A ticket.

**(c) ETags must be durable, not in memory.** `complete_upload` requires the
full `[{part_number, etag}, …]` list and rejects a multipart completion without
it `[repo]`. On iOS the app may be terminated and relaunched several times
during one upload (§3), so each ETag has to be written to disk in the delegate
callback that receives it, not accumulated in a property.

## 2. What a background upload must do, in one paragraph

Slice the source video at `part_size_bytes`; hand each slice to the platform's
background transfer mechanism; survive the app being suspended, terminated and
relaunched; persist `{game_id, upload_id, part_size, per-part URL, per-part
state, per-part ETag}` durably across all of that; and finally call
`POST /games/{id}/uploads/complete` with every ETag in order. The two platforms
differ in exactly one structural way: **iOS must materialise each slice as a
file on disk; Android does not.** That asymmetry drives most of §5.

## 3. iOS — `URLSession` background configuration

All `[docs]` unless marked otherwise.

### 3.1 The file-only constraint

A background session "hands control of the transfers over to the system, which
handles the transfers in a separate process… this configuration makes it
possible for transfers to continue even when the app itself is suspended or
terminated"
([`background(withIdentifier:)`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:))).

That separate process is the reason for the constraint the ticket names: the
transfer outlives your process, so the body cannot live in your process's
memory. It must be a file the system can read on its own. The practical
statement of this — *only upload tasks from a file are supported; uploads from
a data instance or a stream fail after the app exits* — appears in Apple's older
URL Loading System programming-guide material and in the runtime error
developers hit (`Upload tasks from NSData are not supported in background
sessions`, [Apple Developer
Forums](https://developer.apple.com/forums/thread/110328)). **I could not find
it restated on the current reference pages I was able to reach**, so treat it as
strongly-supported-but-unverified rather than quoted-from-current-docs:
`uploadTask(with:fromFile:)` is documented, `uploadTask(with:from:)` and
`uploadTask(withStreamedRequest:)` are documented, and none of the three current
pages says which are legal in a background session.

**Confirming this is step 0 of the device test** (§6, test I-0). It is a
five-minute check and the entire temp-file design hangs off it.

### 3.2 Scheduling: the part that will surprise people

> "The session object applies the value of this property only to transfers that
> your app starts while it is in the foreground. For transfers started while
> your app is in the background, the system always starts transfers at its
> discretion — in other words, the system assumes this property is `true` and
> ignores any value you specified."
> — [`isDiscretionary`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/isdiscretionary)

And discretionary means: "the system might delay transferring large files until
the device is plugged in and connected to the network via Wi-Fi."

This is the crux of the iOS risk, and it is **not** about throughput. Our 12 h
TTL is generous on bandwidth: a 2 GB upload needs 0.40 Mbps sustained and a
cap-sized 8 GB upload needs 1.59 Mbps sustained to finish inside the window
`[arithmetic]` — under any uplink that could have started it, which is the
reasoning already recorded in `config.py` `[repo]`. The risk is that iOS does
not *start* at all: a phone on cellular, off charge, can sit at zero bytes for
hours by design. If that idle stretch exceeds 12 h, §1.3(a) fires and the whole
upload is lost.

Note the shape of the trap. The first part is enqueued while the app is in the
foreground (the user just tapped Upload), so it is *not* forced discretionary.
Every subsequent refill happens after a background relaunch, and those **are**.
So an upload can start briskly, look fine, and then stall — which is precisely
the failure a five-minute test does not catch and an overnight test does.
Test I-2 and I-7 exist for this.

Mitigations available to CF-323: `earliestBeginDate`, and
`countOfBytesClientExpectsToSend` / `countOfBytesClientExpectsToReceive`, which
Apple describes as helping "the system schedule network activity efficiently"
([Downloading files in the
background](https://developer.apple.com/documentation/Foundation/downloading-files-in-the-background)).
Setting the expected byte counts is cheap and should be done regardless. Whether
it materially changes scheduling is `[TO MEASURE]`.

### 3.3 Termination, relaunch and the enqueue window

- Same identifier, new session, on relaunch: "If an iOS app is terminated by the
  system and relaunched, the app can use the same `identifier` to create a new
  configuration object and session and to retrieve the status of transfers that
  were in progress at the time of termination."
- **Force-quit is fatal and documented as such:** "If the user terminates the
  app from the multitasking screen, the system cancels all of the session's
  background transfers. In addition, the system does not automatically relaunch
  apps that were force quit by the user."
- `sessionSendsLaunchEvents` defaults to `true`: "the system automatically wakes
  up or launches the iOS app in the background when the session's tasks finish
  or require authentication," calling
  `application(_:handleEventsForBackgroundURLSession:completionHandler:)`.
- That callback fires **when tasks finish**, not while they are in flight: "At
  launch time, the app does not call this method if there are uploads or
  downloads in progress but not yet finished. If you want to display the current
  progress of those transfers… you must recreate the session object yourself."
- `timeoutIntervalForResource` defaults to 7 days — comfortably beyond our 12 h
  TTL, so it is not the binding constraint.

The design consequence is the important bit. **If the module enqueues only a
few part tasks at a time, each refill requires the app to be relaunched.** That
works — it is exactly what `sessionSendsLaunchEvents` is for — but only if every
piece of upload state is on disk, because the process doing the refill may be
brand new. It also means the wake-up cadence is the system's, not ours.

The alternative is to enqueue all N part tasks up front, which needs all N
slices on disk simultaneously. See §5: that is the difference between ~100 MiB
and 8 GB of scratch space.

### 3.4 Source-file handling

The video comes from the camera roll. A naïve `PHAssetResourceManager` export
writes a second full copy into the app sandbox *before* any slicing begins —
8 GB of source becomes 16 GB on disk before a single part exists. CF-323 should
stream the `PHAssetResource` and write slice files as it goes rather than
exporting whole. Whether that is workable for every asset type (in particular
HEVC and slow-motion assets that may need transcoding on export) is
`[TO MEASURE]`, and it belongs in test I-8.

## 4. Android — `WorkManager` + a foreground service

All `[docs]` unless marked otherwise.

### 4.1 The good news: no temp files needed

Android has no equivalent of the separate-process constraint. The upload runs in
*your* process, kept alive by a foreground service, so the request body can read
straight from the picker's `content://` URI at an offset. **Android needs zero
scratch disk for slicing** — a structural asymmetry with iOS that §5 quantifies.

### 4.2 Doze

> "Suspends network access." … "Doesn't let `JobScheduler` run." … "`WorkManager`
> uses `JobScheduler` internally, so `WorkManager` tasks don't run."
> — [Doze and App
> Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)

Deferred work resumes in maintenance windows, which "the system schedules… less
frequently" over time. A plain `WorkManager` worker is therefore *not* enough
for a multi-GB upload: it will be suspended for long stretches. This is why the
ticket pairs it with a foreground service — an app "with a process currently in
the foreground, either as an activity or foreground service" is not idle.

### 4.3 The Android 14 / 15 foreground-service rules

- **Android 14 (API 34)** made the type mandatory: "Beginning with Android 14
  (API level 34), you must declare an appropriate service type for each
  foreground service." For us that is `dataSync`, requiring
  `FOREGROUND_SERVICE_DATA_SYNC`, `android:foregroundServiceType="dataSync"` and
  `FOREGROUND_SERVICE_TYPE_DATA_SYNC` at `startForeground()`
  ([service types](https://developer.android.com/develop/background-work/services/fgs/service-types)).
- **Android 15 (API 35)** capped it: "The system permits `dataSync` and
  `mediaProcessing` foreground services to run for a total of 6 hours in a
  24-hour period," after which `Service.onTimeout()` is called, the service is
  no longer a foreground service, and "if the service does not call
  `Service.stopSelf()`, the system throws an internal exception"
  (`RemoteServiceException: A foreground service of type … did not stop within
  its timeout`)
  ([FGS timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout)).
  Crucially: "if the user brings the app to the foreground, the timer resets and
  the app has 6 hours available."
- Android 15+ also bars launching a `dataSync` FGS from `BOOT_COMPLETED`.

**Six hours is comfortably more than a 2 GB upload needs and is a real ceiling
for an 8 GB one on a slow link** — but it is *cumulative across the day*, so a
filmer uploading several games from a tournament can exhaust it. CF-324 must
implement `onTimeout()` and stop cleanly rather than crash, and must be able to
resume from the parts already uploaded — which loops back to §1.3(a).

Google explicitly steers away from a bare `dataSync` FGS. The migration guide
points at **user-initiated data transfer jobs** (`JobInfo.Builder.setUserInitiated`),
which is "appropriate if… the user began the data transfer, you need to keep the
user notified of the data transfer progress, [and] it is detrimental to user
experience if the system interrupts the transfer"
([datasync-migration](https://developer.android.com/about/versions/15/changes/datasync-migration)).
That is a precise description of our case. **CF-324 should evaluate a UIDT job
before committing to a plain `dataSync` foreground service**, and the device
test should cover whichever it picks.

Also worth recording from that page: "WorkManager is free to cancel and retry a
job if necessary… Make sure you design and test your workflow to make sure the
cancel-and-retry cycle works properly." Our per-part retry is idempotent (a
re-PUT of the same part number replaces it), so this is safe — but only if the
worker's state is read from disk on each run rather than assumed.

### 4.4 OEM battery managers

There is no primary documentation, because the behaviour is not Android's — it
is Samsung's, Xiaomi's and OnePlus's. Nothing in the platform API turns it off,
and the ticket already accepts this ("only user guidance, so decide what we tell
the user" — CF-324). The community reference is
[dontkillmyapp.com](https://dontkillmyapp.com/), which is a catalogue of vendor
behaviour, **not** a specification, and should be cited as such.

What this means for the test: an OEM device must be tested **at its factory
battery settings**, not with the app whitelisted. Whitelisting first and
measuring second answers a question nobody asked. Test A-5 covers both, in that
order.

## 5. Part size — the arithmetic, and a provisional recommendation

### 5.1 Temp-file disk cost

**iOS only** (§4.1: Android needs none). Two designs, and naming the choice is
half the point of this section.

**Rolling window** — keep at most `C` slice files on disk, delete each on
completion, write the next `C` when the app is next awake. Peak scratch is
`C × part_size` `[arithmetic]`. `web/src/lib/upload.ts` uses `CONCURRENCY = 3`
`[repo]`, which is the natural starting value:

| part size | peak scratch at C=3 | peak scratch at C=1 |
|---|---:|---:|
| 100 MiB | 300 MiB | 100 MiB |
| 64 MiB | 192 MiB | 64 MiB |
| 32 MiB | 96 MiB | 32 MiB |
| 16 MiB | 48 MiB | 16 MiB |

Independent of file size: 2 GB and 8 GB cost the same peak. `[arithmetic]`

**All up front** — write every slice, enqueue every task, let the system drain
them without ever waking the app. Peak scratch is the whole file:

| file | peak scratch, any part size |
|---|---:|
| 2 GB | 2 GB |
| 8 GB | 8 GB |

`[arithmetic]`. On a 128 GB phone that is already full of video, 8 GB of scratch
on top of an 8 GB source is not a cost we can ask for. **Rolling window is the
recommendation**, at the price of depending on background relaunch (§3.3) for
every refill.

Add the source-copy question from §3.4: if CF-323 has to export the asset whole
before slicing, peak disk becomes `file_size + C × part_size` and the part size
stops mattering. Test I-8 settles it.

### 5.2 Retry cost

A failed part re-sends the whole part `[repo]` — that is the stated reason
multipart exists here (`config.py`). Wasted transfer time per failure, at a
representative 5 Mbps cellular uplink `[arithmetic]`, is 168 s for a 100 MiB
part against 54 s for a 32 MiB part. The real per-part failure rate on a phone
walking out of a gym is `[TO MEASURE]` and is the whole reason test A-4/I-4
exist.

### 5.3 Recommendation

**Provisionally: drop `upload_part_size_bytes` to 32 MiB.** The reasoning:

1. It cuts iOS peak scratch from 300 MiB to 96 MiB at C=3 `[arithmetic]` — the
   difference between "fine on a full phone" and "might fail on a full phone".
2. It cuts wasted bytes per failed part by ~3× `[arithmetic]`, on the link where
   failures are most likely.
3. Everything it costs is measured and small: 256 URLs and 136 KiB of ticket for
   a cap-sized file, and 65 ms of signing `[measured-here]`.
4. It is a config change, not a protocol change `[repo]` — `plan_part_count` and
   `planParts` both read it, and 32 MiB is far above R2's 5 MiB minimum.
5. It does not touch `single_put_max_bytes`, which stays 100 MiB. Files between
   32 and 100 MiB keep going as a single PUT — and note that on iOS *that*
   single PUT still needs a 100 MiB temp file, so 100 MiB remains the floor on
   iOS scratch space no matter what part size we choose.

**This recommendation flips if the device test shows any of:**

- **Per-task overhead dominates.** If iOS's background scheduler adds meaningful
  latency per task, 256 tasks may finish materially slower than 82. Measure
  wall-clock for the same 2 GB file at both sizes (test I-6). If 32 MiB is more
  than ~20 % slower, go to 64 MiB.
- **Refill cadence is the bottleneck.** If each background relaunch only manages
  a few parts before the app is suspended again, more parts means more relaunch
  cycles, and larger parts win. This is the most likely way the recommendation
  flips, and I-6 is designed to expose it.
- **iOS turns out to require all slices up front** (i.e. rolling refill does not
  actually work on device, test I-5 fails). Then peak disk is the file size and
  part size is irrelevant to it; pick on retry cost alone, and 32 MiB still
  wins — but CF-323's whole design changes and §8 applies.
- **The 6 h `dataSync` cap binds on Android** for cap-sized files. It does not
  change the best part size, but it changes whether 8 GB is achievable at all on
  one FGS budget, which is a `max_upload_bytes` conversation, not a part-size
  one.

Do **not** change the setting until the device test is run. The current 100 MiB
is correct for the browser, where none of the above applies.

## 6. The on-device test protocol

This is the part of CF-317 that still has to happen. It is written to be
executable by someone with two phones and no memory of this document.

### 6.1 Devices

| # | platform | requirement | why |
|---|---|---|---|
| D1 | iOS | iPhone, current shipping iOS major | the target |
| D2 | iOS | iPhone, one major behind D1 | background-session behaviour has changed between majors before |
| D3 | Android | Pixel, current major, app **targeting API 35+** | the 6 h `dataSync` cap only applies to apps targeting Android 15+ `[docs]`; a lower target silently skips the thing we are testing |
| D4 | Android | **Samsung (One UI) or Xiaomi (HyperOS/MIUI)** — mandatory | §4.4. Without this the Android answer is unearned |

D2 is nice-to-have; D1, D3 and D4 are not. Record exact model and OS build for
each — these results are only meaningful against a stated build.

### 6.2 Fixtures

- **F-2GB** — a ~2 GB `video/mp4`. The ticket's headline case.
- **F-8GB** — a file just under `max_upload_bytes` (8 GiB) `[repo]`. The cap case.
- Both should be real video, not `/dev/urandom`: HEVC from an actual iPhone for
  the iOS source-export path (§3.4), and something from the Android picker for
  the scoped-storage path.

Run against a **real staging api and a real R2 bucket**. A local mock will not
reproduce the 12 h TTL, the 403-on-expiry, or R2's part handling.

### 6.3 Instrumentation

Set this up *before* the first run; several tests are overnight and are painful
to repeat.

**Both platforms — the server-side ground truth.** Point `aws s3api list-parts`
at the R2 bucket with the same credentials the api uses, polled every few
minutes, logging `{PartNumber, Size, LastModified}`. This is the only
observation that does not depend on the app being alive, and it is what turns
"it seemed stuck" into a timestamped stall. (Our api has no `list_parts`
wrapper `[repo]`, so use the AWS CLI directly.)

**iOS.** Install the **Background Networking Profile** from Apple's [Bug
Reporting](https://developer.apple.com/bug-reporting/profiles-and-logs/) page —
Apple names it specifically for "more visibility into how the system is
scheduling and performing your background tasks" `[docs]`. Plus `log stream` /
Console.app, and an append-only log file in the app container (download it via
Xcode → Devices → app container) recording, per event: timestamp, part number,
bytes sent, task state, and **process launch id**, so relaunches are countable.

**Android.** `adb logcat`; `adb shell dumpsys jobscheduler`,
`dumpsys deviceidle`, `dumpsys activity services <pkg>`; Battery Historian for
the overnight runs.

**Disk (iOS, the measurement the acceptance criterion names).** Sample the
scratch directory's size every 10 s for the whole run and record the **peak**,
not the average. A rolling-window design that briefly holds four slices instead
of three is only visible in the peak.

### 6.4 iOS tests

Screen physically locked means the lock button was pressed, not that the app was
backgrounded. The ticket is explicit about this and it is the whole point.

| id | test | procedure | pass |
|---|---|---|---|
| **I-0** | file-only constraint | enqueue an `uploadTask(with:from:)` (Data) on a background session; observe | the error is raised (settles §3.1). **Run this first** |
| **I-1** | 2 GB, locked, Wi-Fi, charging | start F-2GB, lock immediately, do not touch the phone | completes with no user interaction |
| **I-2** | 2 GB, locked, cellular, on battery | as I-1, Wi-Fi off, unplugged | completes; **record time-to-first-byte separately** — this is where discretionary scheduling shows up (§3.2) |
| **I-3** | system termination | I-1, then terminate the app process mid-transfer (Xcode stop, or memory pressure) | transfer continues; app relaunches; upload completes |
| **I-4** | network interruption | I-2, toggle airplane mode for 60 s at ~40 % | the affected part retries; no duplicate or corrupt part in `list-parts` |
| **I-5** | rolling refill | instrument how many slice files exist at once, and how many process launches occur | peak scratch ≈ `C × part_size` (§5.1) and the upload still finishes. **If this fails, §8 applies** |
| **I-6** | part-size comparison | same F-2GB, same link, at 100 MiB and at 32 MiB | record wall-clock, relaunch count and peak scratch for both. This is the input to §5.3's flip conditions |
| **I-7** | 8 GB overnight | F-8GB, locked, cellular, on battery, left overnight | completes **inside the 12 h TTL**. A 403 here is §1.3(a) confirmed in the wild |
| **I-8** | camera-roll source | upload straight from a Photos asset, not a file already in the sandbox | peak disk does not include a whole second copy of the source (§3.4) |
| **I-9** | force-quit | swipe the app away from the multitasking switcher mid-transfer | expected to **cancel** — this is documented behaviour `[docs]`, so the test records what the user sees, and CF-330 needs a story for it |

### 6.6 Pass / fail thresholds

Apply per test, and record the verdict verbatim.

- **PASS** — completes with the screen locked and no user interaction, within
  **2×** the wall-clock the same file takes in the foreground on the same link.
- **CONDITIONAL PASS** — completes, but only under a condition the user did not
  choose (charging only, Wi-Fi only, app whitelisted, needed a foreground visit).
  **Record the condition; a conditional pass is a product requirement**, because
  it becomes something the app has to tell the filmer.
- **FAIL** — does not complete, requires the user to reopen the app, or exceeds
  the 12 h URL TTL.

Any 403 from R2 during a run is `[repo]` §1.3(a) and should be called out
separately from a platform failure — it is our bug, not Apple's or Google's.

## 8. If a platform fails — what CF-323 / CF-324 must do instead

Pre-committing these means the device tester does not have to design a fallback
at 2 a.m.

**If iOS I-1/I-2 fail (background transfer does not survive a locked screen).**
This would contradict Apple's documentation, so suspect the implementation
first: check the session really is a background configuration, that the upload
is `fromFile:`, and that the app was not force-quit (I-9). If it survives
verification, the epic's reason-one justification is in question and CF-313
needs revisiting, not just CF-323.

**If iOS I-5 fails (rolling refill does not work).** The refill depends on the
app being relaunched between batches. If the system does not relaunch reliably,
CF-323's options are: enqueue all parts up front and accept file-sized scratch
(§5.1 — and then gate uploads on free disk, and probably lower
`max_upload_bytes` on iOS); or enqueue all parts up front only for small files
and refuse background mode above a threshold, telling the user to keep the app
open. Both are worse. This is the result most worth knowing early.

**If iOS I-7 fails on a 403 (TTL expiry).** This is our api, and it is fixable
without touching the native module. It needs a Lane A ticket for two endpoints
or one combined endpoint:
`GET /games/{id}/uploads/parts` (which parts R2 already has, via `list_parts` —
not currently wrapped `[repo]`) and a re-presign that issues fresh URLs for the
remaining parts of an existing `upload_id`. Both are small. **File this ticket
regardless of whether I-7 fails** — §3.2 makes a multi-hour stall the normal
case on iOS, and §1.3(b)'s 24 h sweep needs the same fix to know not to sweep a
live upload.

**If Android A-3 fails (Doze kills it).** The foreground service is not doing
its job — check the type is `dataSync`, the permission is declared, and
`setForeground()` is actually called. If it still fails, move to a user-initiated
data transfer job (`setUserInitiated`), which Google names as the right tool for
exactly this `[docs]` §4.3.

**If Android A-5 fails at factory settings (OEM battery manager).** Expected on
at least one vendor, and CF-324's acceptance criterion already anticipates it
("documented, even if the answer is user guidance"). The deliverable is then a
product one, not an engineering one: CF-330's upload screen needs a
vendor-detected prompt directing the user to the battery setting, and CF-344's
error-states pass needs a "your phone stopped this upload" state that explains
why. Neither is a native-module change.

**If Android A-7 fails (6 h cap hit on 8 GB).** `onTimeout()` handling is
mandatory either way. Beyond that the honest answer may be that 8 GB is not
uploadable in one background session on Android 15+ from a phone on cellular,
and the fix is resume-across-sessions — which is the same re-presign endpoint
the iOS TTL fix needs. One ticket serves both.

## 9. Summary of what is and is not established

**Established here, from the code and from primary documentation:**

- The exact part counts, URL sizes and ticket sizes at every candidate part
  size, signed through our own code path `[measured-here]`.
- Signing cost is negligible even at 512 parts `[measured-here]`.
- Temp files are an **iOS-only** cost; Android needs none `[docs]`.
- Peak scratch is `C × part_size` for a rolling window and `file_size` for
  all-up-front `[arithmetic]`.
- iOS forces discretionary scheduling for anything started in the background,
  and our 12 h TTL has no renewal path — the two combine into the largest single
  risk, and it is **an api gap we can close ourselves** `[docs]` + `[repo]`.
- A user's next presign can sweep away their own in-flight background upload
  after 24 h `[repo]`.
- Android's `dataSync` cap is 6 cumulative hours per 24, resettable by
  foregrounding the app `[docs]`.

**Not established, and not guessable from here:**

- Whether a 2 GB upload actually survives a locked screen on either platform,
  and for how long. `[TO MEASURE]`
- The real temp-file disk cost on a device, as opposed to the arithmetic.
  `[TO MEASURE]`
- Whether 32 MiB or 100 MiB parts finish faster in background conditions.
  `[TO MEASURE]`
- What an OEM battery manager does to us at factory settings. `[TO MEASURE]`
- Whether the file-only constraint on iOS background uploads still holds as
  documented (§3.1). `[TO MEASURE]`

The acceptance boxes on [#367](https://github.com/ClipFarmVB/ClipFarm/issues/367)
that depend on those five are deliberately left unticked.
